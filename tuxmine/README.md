# tuxmine

Everything that makes the tuxmine server different from stock GT New Horizons, distributed with [packwiz](https://packwiz.infra.link/). That means our own mods (DaveBridge, GregGuns, later TrainHorizons), extra third-party mods the server runs, and server-specific config.

There are **two separate packs**, because clients and the server need different things:

| Pack | Folder | Used by | Contents |
|---|---|---|---|
| `tuxmine-client` | `client/` | Every player's Prism instance, via a pre-launch command | Our mods (DaveBridge, GregGuns, Fortunate One), WorldEdit + WorldEdit CUI, JourneyMap Unlimited (in place of GTNH's fairplay build), shared config (`findit.cfg`, `fortunateone.cfg`) |
| `tuxmine-server` | `server/` | The GTNH server container, via itzg's `PACKWIZ_URL` | Our mods (DaveBridge, GregGuns, Fortunate One), WorldEdit, server-only mods (DiscordIntegration, the JourneyMap "unlimited" server build), config GTNH doesn't ship (`fortunateone.cfg`) |

Both sit on top of stock GTNH. Players and the server still get the GTNH pack itself the normal way; the packs only add our files.

When the server moves to a new GTNH version, update this table and check every file in both packs.

## Layout (each pack)

| Path | Contents |
|---|---|
| `pack.toml` | Name, version, index hash, MC and Forge versions |
| `index.toml` | Every file with its hash. Generated by `packwiz refresh`; never edit by hand (except to set `preserve`, see **Configs**) |
| `mods/*.jar` | Our own jars, stored as plain files |
| `mods/*.pw.toml` | Third-party mods as URL metafiles (`packwiz url add --force <name> <url>`): URL, sha256, and `side` |
| `config/` | Config overrides (read **Configs** first) |
| `.packwizignore` | Files in the folder that aren't part of the pack |

## Configs

packwiz-installer **overwrites** files it manages whenever the pack changes.

- **Client pack:**
  - A config that must match for everyone: plain file.
  - A default players may change: `preserve = true` on its index entry, so it's only created when missing.
  - **Never ship `config/davebridge-client.cfg`.** It holds each player's own `clientEvalAllowed` opt-in.
  - **`config/findit.cfg` is client-side only in effect.** FindIt runs block and item searches on the server, so `SearchRadius`, `MaxResponseSize` and `SearchCooldown` come from the server's copy, which goes through `COPY_CONFIG_SRC` (`/opt/gtnh/static/gtnh2/config/findit.cfg`, 30/30/160) because GTNH ships that file. The client copy is still shipped for what the client reads itself: the highlight durations and colour, view rotation, and the radius for items on the ground. Keep the shared values the same in both copies.
- **Server pack:**
  - itzg runs **packwiz first, then the GTNH generic pack**. On a GTNH update the pack zip is copied over `/data` *after* packwiz, so any server config that **also exists in GTNH** would be overwritten. Those overrides keep going through the existing `COPY_CONFIG_SRC=/extras/gtnh2` path (`/opt/gtnh/static/gtnh2`), which runs last and always wins.
  - The server pack only carries mods, and config files GTNH doesn't ship.
- **Never put secrets in either pack:** the DaveBridge `authToken`, the Discord bot token, RCON. Everything is served publicly at `https://pack.example.net/`.

## Hosting: `https://pack.example.net/`

The deployment files are in `deploy/`, and the owner's step-by-step is `deploy/DEPLOY.md`.

```
player ──HTTPS──> Nginx Proxy Manager (proxy-host.example.net, :443, TLS) ──HTTP──> desktop :8073 ── caddy ── /opt/gtnh/packs (read-only)
gtnh_2 ──HTTP──> caddy:8073 (inside the gtnh stack network)
```

```
https://pack.example.net/<token>/client/pack.toml         client pack
https://pack.example.net/<token>/server/pack.toml         server pack (the server uses http://caddy:8073/<token>/server/pack.toml)
https://pack.example.net/<token>/tuxmine-<version>.zip    Prism instance zip (below)
https://pack.example.net/<token>/                 one-page player instructions (index.html, written by publish.sh)
```

- **A Caddy container in the GTNH compose stack** (`/opt/gtnh`) serves plain HTTP on **port 8073** only.
  - It uses the official `caddy:2.11.7-alpine` image, pinned by digest. There is no custom build, no certificates and no secrets.
  - Nothing on the desktop listens on 80 or 443.
- **TLS ends at Nginx Proxy Manager on the home router**, which already fronts other sites on 443. It proxies `pack.example.net` to `http://<desktop LAN IP>:8073`. No router port forward is needed for 8073.
  - The only unencrypted hop is router to desktop on the home LAN.
  - packwiz still checks every file against `index.toml`.
- **Caddyfile** (`deploy/Caddyfile`): `auto_https off`, one `:8073` site, `file_server` with dotfiles hidden, and `/healthz` for the compose healthcheck.
  - **Headers:**
    - `.toml`: `application/toml`, `Cache-Control: no-cache` (always revalidated, cheap thanks to ETags).
    - `.jar`: `application/java-archive`, cacheable for a day.
    - `.zip`: `application/zip`, cacheable for a day.
  - **Because jars may be cached, a changed jar must get a new file name.** The release flow below already does this.
- **Cloudflare:** prefer DNS only (grey cloud) for `pack.example.net`. The instance zip is about 714 MiB, over Cloudflare's cache-file limit, and large non-web downloads go against the free plan's terms.
- **Publishing** is an rsync from this repo, `scripts/publish.sh <target>` (below), into `/opt/gtnh/packs/`.
- **The server container fetches its pack over the stack network** (`http://caddy:8073/<token>/server/pack.toml`), so an NPM or certificate problem can't stop the server starting. Caddy being down can, and so can the hosts of the URL mods when packwiz has to download one (see **Server**).

## Access control: secret path and rate limits

Everything is published under a **secret path**: `https://pack.example.net/<token>/`.
- **The token** is a shared secret, not per player. It lives in the git-ignored `deploy/secrets/pack-token` (32 hex characters). Never paste it anywhere public; docs and logs say `<token>`.
- **Without it**, every path except `/healthz` is a 404, including `/`. Caddy has no `browse`, and nothing is published at the root. The hostname isn't discoverable either: the certificate is `*.example.net` and DNS uses a wildcard.
- **Where the token is used:**
  - `publish.sh` stages into `<token>/`.
  - `build-instance.py` bakes it into the pre-launch URL.
  - The server reads it as `TUXMINE_PACK_TOKEN` from `/opt/gtnh/.env` (root, 0600) for `PACKWIZ_URL`.
  - `deploy/Caddyfile` never needs it.
- **The player page** is `https://pack.example.net/<token>/`. It's marked `noindex`, has no referrer, and asks players not to share it.
- **Rotating the token:**
  1. Write a new `deploy/secrets/pack-token`.
  2. Rebuild the zip (`publish.sh` refuses a zip built for another token) and publish. The publish deletes the old `<token>/` directory, zips included, so the old link stops working. That is more deletions than usual: if it stops at `--max-delete`, check with `--dry-run` and re-run with `TUXMINE_MAX_DELETE=<n>`.
  3. Update `.env` and recreate `gtnh_2`.
  4. Players re-import the zip, or edit the token in their pre-launch command.
- **The token never appears in script output.** `publish.sh` and `test-local.sh` print it as `<token>`. It does appear in access logs: Caddy's (stdout, so `docker logs caddy`), NPM's on store, and itzg's startup line `Running packwiz installer against URL: …` in `docker logs gtnh_2`. Treat those logs as secret.

**Rate limits**, in NPM on proxy-host.example.net, which sees real client IPs:
- **Files:** `deploy/npm/http.tuxmine.conf` (appended to `/data/nginx/custom/http.conf`) and `deploy/npm/advanced.conf` (host 54's Advanced tab, kept in NPM's database).
- **LAN, docker and tailnet clients** skip every limit.
- **Outside clients** (already US-only through the OPNsense GeoIP forward) get:
  - pack files: 10 requests/s per IP, burst 60
  - zips: 1 download at a time per IP, 3 at a time in total, 3 per minute per IP, each at 25 MiB/s, so zips use at most ~600 Mbit/s of the 5 Gbit/s uplink
- **Over a limit** gets 429 (`limit_req_status`/`limit_conn_status` in `advanced.conf`).
- **Never add `proxy_buffering off`** to host 54: unbuffered, nginx ignores `limit_rate` and zips go out at full speed. For stalled downloads use `proxy_max_temp_file_size 0` and longer timeouts (`deploy/DEPLOY.md` step 2).
- **Testing:** `scripts/test-ratelimit.sh` checks every limit against a stock nginx set up like an NPM proxy host (advanced.conf at server level, proxying to a backend), with an "outside" and a "LAN" docker network.
- **Backups on store:** `database.sqlite.bak-tuxmine-ratelimit-20261101`, `http.conf.bak-…` and `proxy_host-54.conf.bak-…` in the NPM config dir.

## Players: one link

Prism Launcher can create an instance from a zip URL. We publish **`tuxmine-<version>.zip`**, built by `scripts/build-instance.py`. It's the official GTNH 2.9.0 Prism instance for Java 17+ (`Multi_mc_downloads/GT_New_Horizons_2.9.0_Java_17-26.zip`), with four additions and one removal, and nothing else changed (JVM args, Java settings, `mmc-pack.json` and patches are untouched):

- `packwiz-installer-bootstrap.jar` (v0.0.3) in `.minecraft/`. Prism runs the pre-launch command with the working directory set to `.minecraft`.
- In `instance.cfg`: `OverrideCommands=true` and
  ```
  PreLaunchCommand=\"$INST_JAVA\" -jar packwiz-installer-bootstrap.jar https://pack.example.net/<token>/client/pack.toml
  ```
  - **The quotes must be written as `\"` in the file.**
    - GTNH's `instance.cfg` has no `ConfigVersion`, so Prism first reads it with its old-format parser, which strips the backslashes.
    - After Prism saves it, it is a QSettings INI file, and there a bare `"$INST_JAVA" -jar …` is read as `$INST_JAVA-jar …`.
    - `\"` reads correctly in both, and it's what Prism itself writes.
  - `$INST_JAVA` is the instance's Java path. Prism substitutes it and then splits the command, so a path with spaces works.
- `servers.dat` with **tuxmine** (`example.net:25567`) first; servers already listed are kept. GTNH's zip ships none.
- **Removed:** `mods/journeymap-1.7.10-5.2.23-fairplay.jar`. The client pack installs JourneyMap Unlimited instead, and packwiz never deletes files it didn't install, so the fairplay jar has to go here or both would load. `REMOVE` in the script lists it, and the build fails if a new GTNH zip no longer has that file.
- An icon, Dave's face: the 8×8 head front of `dave.png`, scaled to 128×128 with nearest-neighbour, at `tuxmine_dave.png` in the instance root, with `iconKey=tuxmine_dave`. Prism installs `<iconKey>.png` from the instance root on import.

Player setup: **Prism → Add Instance → Import → paste `https://pack.example.net/<token>/tuxmine-<version>.zip`**, use Java 17+, and launch. A small packwiz window syncs our mods, then the game starts.

- **Prism names the new instance after the zip's file name** (`tuxmine-<version>`), not after `name=` in `instance.cfg`: the import dialog's name always wins. We still set `name=tuxmine (GTNH 2.9.0)`. Players can rename the instance.
- **Our mods** update by themselves on every launch. If the pack host is down, the launch stops with "Pre-Launch command failed".
- **A new GTNH version** needs a new instance zip:
  1. Update the URL and sha256 pins in `scripts/build-instance.py`.
  2. Rebuild.
  3. Publish.

  A new *client pack* version does not need a new zip: existing instances pick it up on their next launch.

**Why the zip is about 714 MiB (decided 2026-10-31, keep it).** It's almost entirely stock GTNH: 473 MiB of mods and 215 MiB of `config/` (mostly txloader textures and sounds, plus the GuideNH guide zip). Our additions are about 50 KB. Smaller options were looked at and rejected:
- **A Modrinth `.mrpack`** can't express the instance's custom Prism components (LWJGL 3 and the two lwjgl3ify patches) or the pre-launch command.
- **Importing GTNH's official zip, then adding our layer by hand**, puts a manual, quote-sensitive step on every player.
- **A thin zip whose packwiz pack pulls GTNH's mods from upstream URLs** is brittle.

Only a few players download it, once per GTNH release, so the size is acceptable.

The zip repackages GTNH's own client release. Serve it only to this server's players.

## Server: `PACKWIZ_URL`

The server uses `itzg/minecraft-server:java25`, `TYPE=CUSTOM` with `GENERIC_PACK`. Its start script runs `handlePackwiz` before `handleGenericPacks`. That step is packwiz-installer v0.5.14 from `link.infra.packwiz:packwiz-installer:dist`, run as `java -cp … link.infra.packwiz.installer.Main -s server`.

The compose changes are in `deploy/compose.snippet.yaml`, and the owner merges them by hand because the compose file is root-owned and live:

- a `caddy` service (`8073:8073`, read-only root, all capabilities dropped except `NET_BIND_SERVICE`, healthcheck on `/healthz`);
- for `gtnh_2`:
  - add `PACKWIZ_URL: "http://caddy:8073/<token>/server/pack.toml"`;
  - delete `MODS`;
  - add `depends_on: caddy: condition: service_healthy`.

**Behaviour verified locally** (`scripts/test-local.sh`, and the itzg script read at master):

- **With `PACKWIZ_URL` set, itzg exits if packwiz-installer fails**, so a broken publish or a stopped Caddy blocks the server's next start.
- **Restarts.** `depends_on: caddy: condition: service_healthy` only applies to `docker compose up`. After a host reboot or a docker daemon restart, docker starts containers in no particular order, so `gtnh_2` can run packwiz before Caddy is up and exit. `restart: unless-stopped` (live) starts it again, with docker's growing back-off, until Caddy answers, so the server comes up a little late, not never.
- **URL mods come from their own hosts, not from Caddy.** DiscordIntegration (edge.forgecdn.net), JourneyMap Unlimited (cdn.modrinth.com), WorldEdit and Fortunate One (github.com) are downloaded whenever one is missing or changed: after a pack change that touches it, or after `mods/` was wiped (`REMOVE_OLD_MODS`, a GTNH upgrade). If that host is down at that moment, packwiz fails and the server doesn't start until it's back (or the mod is shipped as a plain jar instead). The same applies to a player's first sync. On an ordinary restart all mods are already there ("already exists (validated)") and nothing is downloaded.
- **Delete the `MODS` key entirely; don't set it to `""`.**
  - An empty-but-set `MODS` makes itzg's `mcopy` clean up the jars it installed earlier. Those have the same file names packwiz installs, and `mcopy` runs after packwiz.
  - With `MODS` gone, packwiz adopts the existing identical jars ("already exists (validated)") and you get one copy of each.
- **packwiz-installer restores managed files that went missing even when the pack is unchanged.** So `REMOVE_OLD_MODS`, which runs before packwiz, or wiping `mods/` during a GTNH upgrade is harmless.
- **A GTNH generic-pack update only deletes files listed in GTNH's own previous `manifest.txt`**, never ours.

**Migration notes:**
- GregGuns is currently a hand-placed `gregguns-<commit>.jar` in `/data/mods`. The server pack now ships the same `gregguns-2ea0ea5.jar`, which packwiz adopts as "already exists (validated)". If the live jar's name differs from the pack's when you switch, delete the hand-placed one, or there will be two copies.
- Try the whole change on a throwaway itzg container on the `gtnh_default` network before the live server (`deploy/DEPLOY.md` step 6). `gregguns-test-server` is on the default bridge network and can't resolve `caddy`.

## Scripts

| Script | Does |
|---|---|
| `scripts/build-instance.py` | Builds `.work/tuxmine/out/tuxmine-<version>.zip`, where the version defaults to the client `pack.toml` version.<br>• Downloads are cached in `.work/tuxmine/cache/` and checked against pinned sha256s.<br>• Prints the zip's size and sha256 and writes a `.sha256` file next to it.<br>• Needs Pillow. |
| `scripts/publish.sh [--dry-run] [--zip PATH] TARGET` | Publishes both packs and the newest instance zip to `TARGET`.<br>• `TARGET` is required, e.g. `deploy@game-host.example.net:/opt/gtnh/packs/`, and must already contain the marker `.tuxmine-packs` (`touch /opt/gtnh/packs/.tuxmine-packs` once on the desktop). An empty remote path (`host:`), `/`, `~` and `.` are refused, because the sync deletes everything else in `TARGET`.<br>• Runs `packwiz refresh` on a scratch copy of both packs and fails if that would change anything (the index is stale) or, in a git checkout, if a pack has uncommitted changes. The packs are never modified, so a refused run stays refused until you refresh yourself.<br>• Copies only `pack.toml`, `index.toml` and the files the index lists, so `.packwizignore`'d files never leave. It refuses known secret files (`config/davebridge-client.cfg`, `config/davebridge.cfg`, `config/Chikachi/`, `server.properties`, player lists, keys, `.env`) and any text file with a secret-looking `…token`/`…password`/`…secret`/`…apikey` value, JSON keys included.<br>• Refuses a zip whose pre-launch URL isn't this token's, and a jar or zip already published under the same name with different content.<br>• Writes `index.html`.<br>• rsyncs with `--delay-updates --delete-after --max-delete=60` (`TUXMINE_MAX_DELETE`). Older `tuxmine-*.zip` in the current `<token>/` are kept; everything else not staged (a rotated-out token's directory included) is deleted.<br>• Prints the token as `<token>`. |
| `scripts/test-ratelimit.sh` | Functional test of the NPM rate limits in `deploy/npm/` against a stock nginx proxying like an NPM host (Docker, about 1 min): outside clients get capped and refused with 429, LAN clients don't. |
| `scripts/test-local.sh` | The end-to-end test (Docker, about 20 s once the zip exists). It works on scratch copies in `.work/tuxmine/test/` and runs, in order:<br>• publish's refusals of unsafe targets (empty remote path, `/`, `~`, no marker; `RSYNC_RSH=false`, so nothing connects anywhere);<br>• publish, its `--max-delete` stop, and no token in its output;<br>• the pinned Caddy with the real Caddyfile on 127.0.0.1:18073 (headers, 304s, hidden dotfiles that exist: the marker and rsync's `.~tmp~`);<br>• a server sync with the itzg installer jar;<br>• a client sync with the bundled bootstrap in the extracted instance;<br>• a no-op re-run;<br>• the drift refusal, twice (the pack is left untouched);<br>• refusals of secret files and values, a same-name jar change, and a zip built for another token;<br>• an update, deleting a root-level zip and an old token's directory while keeping this token's older zip;<br>• a removal;<br>• the compose snippet merged onto a stub stack, with `gtnh_2` fetching over the stack network and no `MODS` set.<br>Containers are removed at the end. |

## Releasing an update

1. Build the mod, e.g. `cd ../DaveBridge && VERSION=x.y.z ./gradlew build`.
2. In **each** pack that carries it, replace the old jar in `mods/` with the new one. The new jar must have a new file name (the version is in it), because jars may be cached.
3. Bump `version` in that `pack.toml`.
4. `~/go/bin/packwiz refresh` in that pack.
5. Publish: `tuxmine/scripts/publish.sh deploy@game-host.example.net:/opt/gtnh/packs/` (try `--dry-run` first).
   A zip rebuilt with different content needs a new name too: `build-instance.py --version <new label>`.

Clients pick it up on their next launch, and the server on its next restart.
